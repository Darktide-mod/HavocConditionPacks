# 少敌人时持续低帧：本次证据与计时版

2026-09-12，HCM 4.4.6-test.11 / 狂暴攻势 1.7.1。本次交付是限时诊断版，保留 1.7.0 的原生动画加速、+100% 测试值和跨障碍规则。尚未确定实机持续低帧的主要耗时，不能宣称已经修复。

- 第 2509 行，11:27:03.432：六个单位实际经过状态机和两个混合器入口，`method=engine_dt`。未发现本词条的重复绑定错误或高频诊断输出。
- 这次原生入口确认之后，至 11:29:45 开始退出，日志没有新的 `Stall` 报告。普通低帧可能每帧只花二三十毫秒，不会形成该日志中的百毫秒级卡顿警告；因此没有警告不能证明帧率正常。

本次没有对已退出的游戏做内存附加或执行测试修改。日志核对输出保存在 `build/checks/frenzied-low-fps-log-audit.json`。

## 新方案如何影响每帧

1. **词条自己的 Lua 工作。** 每个参与处理的 AI 更新仍会取得当前攻速并临时切换相应动作数据。世界更新前还会筛选已登记单位、验证其身份、填入原生倍率表。少量可见敌人不等于后台只登记了少量单位，需要实际计数。
2. **全场原生入口。** 四个入口由所有动画对象共用。未登记对象同样进入转接代码，查表未命中后沿原速执行。此开销并不只随屏幕内敌人数变化。现有倍率表每帧清空 512 KiB，但这也不能仅凭大小认定为明显掉帧的来源。
3. **引擎实际执行的动画工作。** 加速改变状态推进、片段结束、过渡、根运动与动画事件的时间分布。引擎仍按自己的实现完成这些工作。此前的 0.39 ms 测试使用模拟引擎函数体，没有测量这一部分，更没有测量渲染等待。
4. **加速后的战斗工作。** 攻击更密集会改变命中、碰撞、特效、音效和增益触发的发生频率。这是可能增加负载的途径；目前没有关／开词条的同条件计时，无法分配其占比，也不能用它替代对少敌人低帧的核查。

## 补做的入口范围实验

在隔离进程执行同一原生转接代码，登记十个选定单位，同时加入 100、1000、10000 个未登记的模拟动画对象；各未登记对象分别调用状态机与两个混合器阶段。对比挂接启用和停用时同样的函数调用，并检查未选对象的时间保持原速。

本次样本的入口差额约为 0.0002、0.0048、0.0423 ms/次，记录在 `build/checks/frenzied-native-scene-scope.json`。这补上了此前未选对象完全缺席的测试范围。在这些地址分布及缓存条件下，单纯查表差额不足以解释明显低帧；真实游戏的对象分布、求值、缓存和多线程调度仍不在该数字内。不能把这一结果当成游戏 FPS 已通过。

## 计时版做什么

test.11 没有改变原生 DLL、挂接 ABI 或转接代码，没有自动切换倍率。新增 Lua 侧的高精度时间采样：

- 每十次指定世界更新采样一次详细阶段；所有有效更新记录墙钟间隔。
- 每十秒输出一条 `[Frenzied perf]` 汇总，三分钟后自动停止；任务提前结束会汇总剩余数据。
- 固定数量的累加项与直方图，不保留每帧明细或逐单位日志，不新增工作线程回调。
- 排除其他世界及暂停间隔。测量时间也有少量成本，因此这里只做有上限的采样。

| 字段 | 含义与判读 |
| --- | --- |
| `fps`、`frame_ms`、`p95_ms`、`max_ms` | 指定世界更新之间的实际间隔统计。`fps` 是该更新频率，不是包含 DLSS 生成帧的显示帧率；p95 为 0.5 ms 分桶，256 ms 桶含更大的间隔 |
| `tracked`、`animated` | 采样帧登记单位数、成功加入加速表的单位数，格式为平均／最大；不是屏幕可见数量 |
| `prepare_ms`、`prepare_max_ms` | 词条的动作策略筛选、身份校验、倍率表准备及发布耗时 |
| `world_ms`、`world_max_ms` | 内层 `ScriptWorld.update` 耗时，包括原生求值、工作任务等待、动画／场景回调及其内部挂接，不是独立的 GPU 或原生转接开销 |
| `after_ms` | 关闭本次倍率作用域及确认逻辑的耗时 |
| `ai_calls`、`ai_own_total_ms` | 采样期间 AI 包装调用数，以及词条自己的准备／恢复总耗时 |
| `ai_inner_total_ms` | 同一批采样 AI 调用的内部耗时，可能包括原版 AI 和其他模组的内层挂接 |
| `node_swaps` | 采样 AI 更新累计涉及的动作节点数，用于判断每个单位是否处理了过多节点 |

AI 回调可能发生在世界更新内部，因此 `world_ms` 与 AI 耗时不能简单相加。世界内层耗时很高仍需要进一步分解；若它和词条自身耗时都很低而帧间隔很高，则持续耗时位于这些区间之外。
